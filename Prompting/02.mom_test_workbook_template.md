## 작성 규칙

| 항목 | 규칙 |
|------|------|
| **페르소나** | 구체적 역할·상황·습관. "모든 사용자" 금지 |
| **인터뷰 답변** | **과거 사실**만. "~하면 좋겠다" 금지 |
| **표면 문제** | 사람들이 **말하는** 문제. 프로그램·기능·기술이 섞인 문장 → **금지 예시**로 분류 |
| **진짜 문제** | **한 문장**. 불편·비용·판정·재현 중심. 솔루션 이름 없음 |

## 워크북 예시 (MagicSquare_xx — 인터뷰 완료본)

### 페르소나

4×4 부분 마방진을 손으로/코드로 다루는 학습자. 재미로 퀴즈처럼 풀거나 코드로 실험.

### 인터뷰 답변 (과거 사실)

1. 재미로 혼자 퀴즈풀듯이 해봤다.
2. 행·열 합부터 계산했다.
3. 빠진 행·열 합 비교 시, 여러 합을 외우기 헷갈렸다.
4. 종이에 작게 적었다.
5. 1분 이내에 풀었다.
6. 행·열·대각선 합을 모두 검증했다.
7. 코드로는 여러 경우의 수 때문에 훨씬 헷갈렸다.
8. 변수 타입 오류, 문제 잘못 출제 가능성을 걱정했다.

### 표면 문제 (금지)

> "4×4 마방진에서 빈칸 2개를 채우는 **프로그램**을 만든다."

### 진짜 문제 (한 문장)

> 손으로 풀 때는 여러 행·열(·대각선) 조건을 동시에 추적·판정하기 어렵고, 코드로 옮기면 입력·타입·문제 출제 오류 가능성까지 겹쳐 **무엇이 맞고 틀린지, 무엇부터 확인해야 하는지** 판단하기 전에 헷갈린다.
